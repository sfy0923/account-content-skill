# 泛话题调用与交接

仅在本轮已明确采用泛话题，或已有内容的有效分支为泛话题时读取。GGB 管理当前项目事实、前置研究、用户确认和最终交付；`ip-general-topics` 处理泛话题选题、方案、写稿、审核、修改与复审。原 GGB 模块继续处理原任务，不与本分支叠加默认结构、数量或评分门槛。

## 1. 先确认范围，再定位 Skill

新 IP 首轮尚未明确类型与范围时，先执行 GGB 主入口的两类各1条询问。明确回复前不研究、不生成；只补充 IP 信息不算接受。明确范围、已有方案确认、审核现稿或局部修改不重复询问。1＋1只指两条选题与核心观点，不自动授权任何整稿。

按稳定名称 `ip-general-topics` 在宿主提供的可用 Skill 清单中查找，读取其实际 `SKILL.md`。调用方明确提供了安装根目录或入口时，也可据此定位，但必须核对入口 frontmatter 的名称。引用资源按该入口实际所在目录解析，不按当前工作目录猜测。

不得写死某台机器的绝对路径，不假定 GGB 真源的同级目录必有子 Skill；目录中有文件也不自动等于宿主已加载。需要记录实际读取入口、所用版本或快照标识及资源取得情况，不能只凭名字宣布调用成功。

本仓库同时分发 `ggb` 与 `ip-general-topics` 两个可独立安装的 Skill。使用泛话题分支时应安装两者；仅安装GGB不会自动证明子Skill可用。仍按上述方式发现入口并读取资源，不从仓库布局猜测安装路径。

这项调用由执行任务的 Agent 读取并执行对应规则完成，不假定存在通用的嵌套 Skill API，也不要求启动另一个模型。只对实际验证过的宿主报告调用可用。

找不到入口、名称不符或本次所需核心 reference 不可读时，返回“依赖不可用”并列明缺项。保留已取得材料，继续与该依赖无关的工作；不得静默套回原五段／3分钟流程、临时拼出替代版本、宣称已经完成子 Skill 调用，或自行安装、下载依赖。

## 2. 六个动作与确认继承

读取子 Skill 主入口及其 `references/handoff.md`，再按入口要求读取当前动作所需模块；不要每次把三个长 reference 全部加载。

| 当前请求 | 传入动作与范围 |
| --- | --- |
| 开发泛话题 | 选题；传入本轮数量、已选／被否内容与去重范围。小样不扩成64条 |
| 用户选题后看方案 | 方案；传入被选题、核心观点、受众、目的、时长与事实边界 |
| 写完整稿且方案已确认 | 写稿；携带对应方案内容、版本和确认记录，不重新问同一确认 |
| 写稿但方案未确认 | 先返回具体方案，状态为“待确认”；确认后续接原写稿任务 |
| 只审现稿 | 审核；传入完整正文与已有画面说明，不重走选题或方案，不自动改写 |
| 修改／继续改 | 修改；传入有效审核问题、保留内容、允许修改范围及版本关系 |
| 复审 | 复审；传入当前稿、原问题、可比较版本与未解决项 |
| 已授权完整审改闭环 | 按需连续审核、修改、复审；只有决定性事实或未确认的核心变化才返回问题 |

当正文成立依赖需要核实的核心专业结论时，先核实并取得必要知识答案确认，再进入方案。仅因题目有“为什么”、内容是主观偏好或感受，不增加答案确认。偶尔使用的背景事实按需要核验，不另加整轮答案审批。上层已确认答案，或已确认方案明确包含并认可该答案时直接继承；新增关键答案与确认不一致时，说明受影响部分。

子 Skill 需要事实或选择时先返回具体缺口；GGB 核对现有对话和项目材料后统一提问。同一问题不让两个入口各问一次。公开事实可核实时先核实；人物经历、本人立场和允许公开范围不能用同行材料代替确认。

局部口语修正不撤销整份方案确认。改变主任务、核心立场、人物定位、素材性质或关键时长取舍时，仅确认受影响变化。批准按建议修改，不等于认可尚未写出的修改稿。

## 3. 前置研究由 GGB 负责

范围确认后，按照 `research.md` 的原条件决定是否研究：新项目材料不足且需要开发方向时，先找并分析相关同行；材料够用、只缺录音、只审现稿或局部修改不重启研究。用户明确只要研究时仍由原研究模块完成，不调用本分支生成内容。

把研究实际取得的材料、可回查来源、分析范围、可迁移方法与未解决项交给子 Skill；Q／V／核心 ID 沿用项目现有编号。研究潜力分与准备度可以保留原用途，但不转换为泛话题合格结论，也不把泛话题再送回原七项90分门槛。

无法取得作品时，按原研究模块如实报告实际范围和限制，可靠公共资料可支持其能证明的候选。区分“同行资料未取得”和“当前内容核心事实不足”：前者不阻止材料已足够的任务，后者暂停依赖该事实的判断。子 Skill 不再次研究或回调 GGB，避免循环。

## 4. 使用已有项目状态交接

只整理当前动作需要的信息，不让用户重填已知背景，不给全部未选候选附长卡。

- **请求与对象：** 本轮动作、数量、修改与输出范围；项目、账号、说话者、受众、目的；每条分支及适用标准。
- **有效要求：** 核心、形式、时长或明确不限时长、口吻、公开边界、结尾与其他须逐字保留的原文、后来解除锁定的范围、拍摄条件及已有授权；连续未解决的反馈随对应版本传递。
- **当前材料：** 选题或完整稿、原话与来源、材料性质和核验状态、假设及待核实项、有效反馈、已核对的历史范围。
- **确认：** 首轮范围回复或委托、运营选题、知识答案和方案确认的内容与版本、IP观点认可、经历核实、允许公开、用户成稿认可、试读实拍分别记录。
- **版本：** 项目与批次、题目原编号、当前稿及来源版本、首稿与目前最好版本、稳定问题编号和处理状态。

没有编号时在当前项目内建立可追踪编号；不能仅凭同名标题跨项目匹配。未知写未知，不把对某一步的同意升级为全部确认。不同客户和账号的经历、店规、数字与表达边界分别保留，不因共用 Skill 而迁移。交接卡与完整内容一同传递，不能替代正文或把作者自评变成证据。

## 5. 接回结果、合并与结束

接回本轮产物、执行状态、更新后的交接、具体未解决项与下一动作。按每条分支保留原判定，不合并成一个总分或笼统“通过”。

| 执行状态 | GGB 的处理 |
| --- | --- |
| 已完成 | 交付本轮动作结果；不自动标成用户认可、可拍或效果验证 |
| 部分完成 | 保留合格部分，核对目标、实际数量、缺额和原因；不偷偷改目标 |
| 待补信息 | 先核对已有资料，合并决定性问题，同时交付可完成部分 |
| 待确认 | 展示具体答案、方案或核心变化；收到明确回复后按对应版本续接 |
| 需转交 | 保留成果和确认，由 GGB 接续当前超范围部分；不让子 Skill 回调 GGB |
| 依赖不可用 | 报告入口或所需规则缺项，不假称调用完成，不改用原分支冒充结果 |

审核结论另保留“通过／局部修改／需要重新诊断”；决定性信息不足时保留有范围的文本初判。审核动作完成不等于稿件通过，文本通过不等于用户或本人认可。

完整稿采用连续纯口播正文与独立拍摄执行表；表格对应正文段落，不维护两套容易冲突的台词。默认预计总时长90至120秒；已指定时长优先。并行口播与画面不重复累加；未试读或实拍，只说明估算。

明确只要纯正文时不附拍摄表；明确不限时长时撤销默认长度，先讲清再估时。继承子Skill关于聊天式口播、具体句意、跨场景连接、固定结尾反查和两轮重诊的检查，不在接回结果时补总结道理或擅改为剧情。规范更新与发布不改变任何稿件的待确认状态。

混合批次或局部修改时按稳定编号合并有效版本，分清“只改哪条”与“只输出哪条”。用户未限定局部输出时交完整最新版，未修改的已确认内容保持一致。不重复计算同一核心，不把非泛话题的评分当泛话题结果。另行要求旧评分时，只作为标明适用限制的比较，不覆盖本分支结论。

复杂多人剧情或多场景表演超出子 Skill 的完整口播执行范围时，接回选题、核心与已见文字的结果；由 GGB 对应能力继续，保留本条已确认核心、时长和形式，不重新套其默认值。

同一 AI 审改复审称审核／复审或自查，记录实际审阅者背景；只有实际发生另一审阅者或独立评审过程时才描述其范围。换执行者但已看过旧反馈不自动称盲审。

只要审核就在审核后结束；有完整审改授权则做必要闭环。允许零问题、零修改、撤回错误意见及部分回退。两轮同一问题未解，重新诊断，不自动放行；只剩可选润色时停止。不得自动发布、上传、安排任务，或把文字判断当作观众和传播验证。
